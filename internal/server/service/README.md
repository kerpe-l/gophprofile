# server/service

Сценарии работы с аватарами: загрузка, раздача, метаданные, удаление. Зависимости
приходят интерфейсами, объявленными здесь же; про HTTP, SQL и MinIO пакет не знает.

## Загрузка

`INSERT (uploading)` → `PUT` в хранилище → `UPDATE (uploaded)` → publish.
Атомарности между тремя системами нет, отсюда порядок и обработка отказов:

- запись создаётся первой: упавший между шагами процесс оставляет запись
  без файла, а не файл, на который никто не ссылается;
- после валидации контекст отвязывается от клиента (`context.WithoutCancel`):
  клиент, оборвавший соединение после заливки, не должен оставить запись
  в `uploading` при уже лежащем файле — такое состояние ничем не подбирается;
- отказ хранилища переводит запись в `failed`, ошибка уходит клиенту;
- отказ публикации загрузку **не** проваливает: аватар остаётся
  `uploaded` + `pending`, и reconciler переопубликует событие — заставлять
  клиента заливать файл заново незачем.

## Раздача

- Миниатюра не готова — отдаётся оригинал с кешем в минуту вместо суток.
- Заглушку отдаёт только `UserAvatarContent`: и когда аватара нет, и когда запись
  есть, а объекта в хранилище нет. `AvatarContent` (по id) — строго `ErrNotFound`.
- Срок жизни в кешах выбирает сервис: готовое изображение — сутки (содержимое
  по ключу не меняется), подмена и заглушка — минуты, иначе готовая миниатюра
  или первый загруженный аватар не подхватятся клиентами.

## Удаление

Сверка владельца → soft delete → событие воркеру на уборку файлов. Синхронно файлы
не удаляются: запрос не должен ждать хранилища. В отличие от загрузки, отказ
публикации здесь проваливает запрос: удалённые записи никто не перебирает,
и файлы остались бы в хранилище навсегда и молча.
